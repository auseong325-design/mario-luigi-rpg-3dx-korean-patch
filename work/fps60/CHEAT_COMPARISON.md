## 2. 자세한 차이

### 2.1 적용 방식과 실기 크래시

- **치트**
  - 작동 방식: Luma의 Rosalina가 50ms마다(약 1초 20번) 게임에 디버거를 붙여 메모리를 읽고 쓴 뒤 뗀다(Luma 소스 `menu.c`, `cheats.c`).
  - 멈추는 원인: 디버거가 붙어 있을 때 게임이 새 스레드를 만들면 3DS 커널의 경쟁 상태로 멈출 수 있다. Luma 공식 README의 "Known issues"에 올라 있는 문제다. 이 게임은 장면이 바뀔 때 불러오기 스레드를 만든다.
  - 사용자 보고: 메뉴와 필드 전환, 전투 시작과 끝, 저장 블록, 거대 전투 시작에서 멈췄다는 보고가 있다(`web.md` §2 R3·R6·R7·R9·R10). 60fps가 아닌 다른 치트만 켜도 멈춘다는 보고(R1)도 있다. 에뮬레이터 사용자에게서는 멈춤 보고가 없다.
- **이번 모드:** Luma가 게임을 불러올 때 코드 파일(`code.ips`)을 한 번 적용한다. 실행 중에는 디버거가 붙지 않으므로 이 원인은 생기지 않는다.
- **실기 상태**
  - 첫 배포판(`code.bps`)은 게임 시작 전에 멈췄다. 원인은 Luma v13.4가 BPS 파일을 처리하는 방식이었고, `code.ips`로 바꿔 해결했다(`work/fps60/runtime/findings.md` §8.10).
  - 그 뒤 몇 분 플레이에서는 크래시가 없었다(사용자 보고). 오래 플레이한 확인은 아직 없다.

### 2.2 무엇을, 언제 바꾸는가

- 이 게임 엔진은 원래 60fps 기준이다. 작업(장면 단위로 도는 프로그램)마다 "30fps로 돌지"를 정하는 1바이트가 있고, 일본판은 필드·전투·쿠파주니어·메뉴 작업을 모두 30으로 만든다. 두 방식 모두 이 값을 60fps 쪽으로 바꾼다는 점은 같다.
- **치트**
  - 정해진 메모리 주소 4곳만 본다. 일본판에서 측정한 위치로 보면 다음과 같다(`findings.md` §1~§6, `analysis/engine.md` §6).
    - 0x320DA3AC: 필드(타이틀 화면 포함)
    - 0x30000044: 전투
    - 0x30000064: 일시정지 메뉴
    - 0x30000074: 파일 선택·저장 메뉴
  - 이 자리에 만들어지지 않은 작업은 바뀌지 않는다. 예: 쿠파주니어 RPG 도입부의 필드 작업은 0x320ABAC8에 만들어졌다. 그래서 치트로는 이 부분이 60fps가 되지 않을 가능성이 높다(추정).
  - 장면이 30fps로 시작한 뒤, 최대 약 50ms 늦게 값을 바꾼다. 장면이 바뀌면 새 작업이 다시 30fps로 만들어진다.
  - Azahar에서 같은 방식으로 값만 바꿔 봤더니, 메뉴나 저장 화면을 열고 닫을 때마다 30fps로 돌아왔다(`findings.md` §6.5~§6.7).
- **이번 모드**
  - 작업이 만들어지는 순간 종류(필드·전투·쿠파주니어·메뉴)를 확인하고, New 3DS이면 처음부터 60fps로 정한다.
  - 장면 전환 77번 이상(쿠파주니어 RPG 진입 포함)에서 모든 새 작업이 60fps로 시작했다(`findings.md` §7.9, §8.7).
- **장면 시작 때 한 번 저장되는 값:** 메뉴 커서 깜빡임 속도 등 28곳이 장면 시작 때 속도값을 한 번 저장해 두고 계속 쓴다. 치트처럼 나중에 바꾸면 이 값이 30fps 기준으로 남는다. 이번 모드는 저장되기 전에 정하므로 맞는 값이 들어간다(`analysis/audit_fps_sites.md`).

### 2.3 60fps에서 빨라지던 것 (치트에는 없는 보정)

Azahar에서 같은 세이브로 쟀다. "보정 없음"은 치트를 쓸 때와 같은 상태다. "스크립트 계산"이라고 적은 칸만 실행하지 않고 전투 스크립트에서 계산한 값이다.

| 대상 | 보정 없음(치트와 같음) | 이번 모드 | 원래 30fps |
|---|---|---|---|
| 쿠파 몸속 미니게임(아드레리버) 조작 루프 | 1초 60번 | 1초 30번 | 1초 30번 |
| 다크스타 매달리기: 손을 0.2초 뗐을 때 | 0.15초 만에 떨어짐 | 버팀 | 버팀(스크립트 계산: 봐주는 시간 0.27초) |
| 다크스타 매달리기: 별 한 바퀴 | 0.81초 | 1.64초 | 약 1.62초(스크립트 계산) |
| 스타&스타 시범: 착탄 → 「EXCELLENT!」 | 331프레임(5.55초) | 240·270프레임 | 210~270프레임 |
| 엔딩 크레딧 글자가 다 올라가는 시간 | 102.9초, 이후 약 102초 정지 | 205.8초 | 205.8초 |

출처: `findings.md` §7.3·§8.2·§8.3·§8.5, `analysis/koikoi_star.md` §6~§11.

- 필드 이벤트 스크립트가 시간을 프레임 수로 세는 곳은 미니게임 말고도 많다. 방 장치, 적 반응, 마을 사람 동작 등 96개 스크립트 139곳이 확인됐다(`analysis/field60.md`). 이번 모드는 스크립트 실행 자체를 1초 30번으로 맞춰 한꺼번에 해결했다.
- 아주 짧게 누른 버튼(17ms)은 34번 중 34번 인식됐다(`findings.md` §8.6).

### 2.4 같은 점과 남은 한계 (두 방식 공통)

- **액션 커맨드:** 일반 공격·형제 어택·피하기·반격의 판정은 원래 실제 시간 기준이라, 두 방식 모두 판정 시간이 30fps와 같다. 치트 사용자의 "액션 커맨드가 망가진다" 보고(R19)에는 어떤 공격인지 적혀 있지 않다. 확인된 원인인 버티기 공격은 이번 모드에서 고쳤다.
- **거대 전투:** 자체 루프(최대 60fps, 시간 보정)로 돌아서 두 방식 모두 영향을 주지 않는다(`analysis/hugebattle.md`). 실제 실행 확인은 아직 하지 않았다.
- **무거운 장면:** 실기에서 한 장면을 1/60초 안에 그리지 못하면 그 순간 게임이 느려진다. 늦어진 만큼 따라잡지 않는다. 두 방식 모두 같다.
- **메뉴 연출:** 장비 화면·상점의 판 미끄러짐과 메뉴 버튼 반복 입력이 2배 빠르다. 1DX 한국판이 60fps에서 보이는 속도와 같고, 두 방식 모두 같다.

## 3. 60fps 모드와 한글 패치를 따로 쓰기

60fps 모드는 파일 두 개다. 둘 다 원본 일본판 v1.2 파일로 만들었고 한국어 글자가 들어 있지 않다.

| 파일 | SD 위치 | 역할 |
|---|---|---|
| `code.ips` (552 B, sha256 `e5aa7d60…998a`) | `luma/titles/00040000001CA900/code.ips` | 60fps 전환, 필드 이벤트 1초 30번 실행 |
| `BAI.dat` (2,861,904 B, sha256 `8f3c1928…7261`) | `luma/titles/00040000001CA900/romfs/BAI/BAI.dat` | 전투 스크립트 보정. 30fps에서는 원본과 동작이 같다 |

- **한글 + 60fps:** 지금 배포 ZIP(`work/sd_package/ml3dx_ko_luma.zip`)을 그대로 쓴다.
- **한글만**
  - 방법: ZIP을 넣은 뒤 `code.ips`만 지운다. `BAI.dat`은 남겨도 된다.
  - 확인: Azahar에서 정상 부팅했고 모든 장면이 30fps였다(`work/review/rt5_20261030/RT5.md` §1b·§3.4).
- **60fps만 (일본어 원문)**
  - 방법: 위 두 파일만 넣는다. `romfs` 안에 다른 파일은 두지 않는다.
  - 확인(2026-10-31 KST, Azahar): 로그에는 `code.ips` 적용과 `/BAI/BAI.dat` 교체만 나왔다. 타이틀·필드·일시정지 메뉴가 초당 60프레임으로 돌았고 글자는 일본어였다(`work/fps60/runtime/jp60_field.png`, `jp60_pause.png`).
- **공통 조건:** 일본판 v1.2 업데이트 설치, Luma "Enable game patching" 켜기. `code.bps`는 쓰지 않고, SD에 남아 있으면 지운다.
- **HOME 메뉴 한글 배너 CIA**(`work/banner_20261030/out/`): 위 두 패치와 상관없이 따로 설치한다.

## 4. 서양판(북미·유럽)에 60fps 모드만 넣기

- **지금 파일은 그대로 쓸 수 없다.**
  - 일본판 v1.2 코드의 주소에 맞춘 패치다.
  - Luma는 타이틀 ID 폴더에서만 패치를 읽는다. 일본판은 `00040000001CA900`, 북미판은 `00040000001D1400`, 유럽판은 `00040000001D1500`이다.
  - 폴더 이름만 바꿔 넣으면 서양판 코드의 엉뚱한 곳을 덮어써 게임이 망가진다. IPS는 게임 버전을 검사하지 않는다.
- **옮기는 것은 가능하다고 본다.**
  - 같은 엔진이다. 서양판 v1.2용 커뮤니티 치트가 쓰는 메모리 주소가 일본판에서 측정한 필드·전투·메뉴 작업 위치와 똑같다. 작업 구조가 같다는 근거다.
  - 코드: 서양판 v1.2 코드에서 같은 역할을 하는 곳을 찾아 `code.ips`를 다시 만든다. 대상은 작업 생성 지점, New 3DS 판별 함수, 대상 작업 종류 4개, 필드 이벤트 처리 자리 6개, 입력 보관 자리, 빈 코드 공간이다.
  - 검사: 지금과 같은 검사(Luma·Azahar 적용 재현, 가상 CPU 시험)와 Azahar 실행 시험을 한다.
  - `BAI.dat`: 서양판 파일과 비교한다. 같으면 그대로 쓰고, 다르면 같은 수정(전투 스크립트 9개 15곳 + 스타&스타 2개)을 다시 적용한다.
  - 서양판도 New 3DS 124MB 모드라면 `code.bps`가 아니라 `code.ips`로 내야 한다(2.1의 Luma v13.4 문제).
- **필요한 것:** 사용자가 가진 서양판 게임(기본 게임 + v1.2 업데이트)의 덤프. 지금 프로젝트에는 일본판 CIA 두 개와 DS판 롬만 있다.
